# 多人同步、检查与上传

## 开始和上传前都同步

确认目录、origin 的 fetch/push 目标、登录账号、仓库写权限、工作树、分支、未推提交及进行中的 Git 操作。认证与规则按 [github-auth.md](github-auth.md) 复核。

在已确认的仓库中运行：

```bash
git status --short --branch
git diff --stat
git diff --cached --stat
git fetch origin
```

检查未跟踪文件与提交日志，区分本次修改和同事未完成成果。提交前检查 diff、敏感配置和构建产物，只 stage 本次应提交的路径；不默认无条件 `git add .`。

工作／集成分支可只存在本地，不要求 PR。默认正常 merge 保留团队历史；不要 rebase 已共享分支。自己未共享的提交可按上下文整理，但不能丢弃已有工作。

## 数据库检查：在可能触发发布的 push 之前做

审查即将上线的**全部范围**，不仅是最后一个 commit：Flyway、Liquibase、SQL、初始化／启动任务、数据导入修复脚本、自动执行这些脚本的配置。普通业务代码出现 SQL 字符串不自动等于一次生产改库，但改变部署时执行行为属于该范围。

出现直接数据库修改时明确告诉用户：

> 这次包含直接数据库修改，请向 xjxl 索要该项目的服务器访问密钥／授权。请通过你们的私密渠道接收并保存在本机受保护的位置，只告诉我本地路径；不要把私钥或数据库密码粘进聊天或提交到 GitHub。

已有适用权限就复用并核验，不重复索要。主机、用户、项目目录和数据库由该项目配置／负责人确认；不套用 `ssh aole` 或他人的路径。

继续本地检查与准备方案；生产操作前完成：

1. 核对具体库、已有迁移历史、版本号、目标数据范围。Flyway 整数版本按数值比较；复杂版本按 Flyway 版本规则，不能用字符串 `MAX(version)` 猜下一个号。
2. 新迁移用新文件；不改已执行文件或删除迁移历史来掩盖校验冲突。
3. 给出 SQL／迁移清单、影响行数的预查询、备份／恢复方式，在隔离本地／测试库验证。
4. 修改／删除现有生产数据及不可逆结构变更：先呈现具体方案，按适用授权执行；一般“上传”不等于任意删除数据授权。确认备份存在且可读、记录恢复路径。持有 SSH 密钥只是连接能力，不替代操作授权。
5. 缺所需密钥、生产迁移历史或备份时，不推会自动部署的 main。若已有流水线会由 test 自动升 main，则 test 也不能先推这批迁移；确认 test 只是暂存分支后才可先推 test，并报告生产发布待处理。

应用镜像回滚不等于数据库回滚。普通代码上传不要一律索取 SSH 密钥。

## 普通项目：正常推 main

1. 从最新 `origin/main` 创建本地工作／集成分支，合入属于本次的提交；已有工作分支可继续用。
2. 列出 main 将新增的全部提交，检查完整 diff；解决冲突后按实际结果运行相关测试、构建与业务验收。无冲突只代表 Git 能合并。
3. 记录已检查提交 SHA，推送前重新 fetch main。main 前进就整合新增提交并重跑受影响检查；不覆盖同事提交。
4. 从最终候选提交**普通推送**到明确的 `refs/heads/main`。可用 `git push origin HEAD:refs/heads/main`，前提是 HEAD 正是刚验证的候选且包含最新远端 main。
5. 非 fast-forward 拒绝说明远端又前进，重新 fetch、整合、验证再推；连续竞态无法收敛时保留成果，说明需协调短暂上传窗口。不用 `--force`／`--force-with-lease`。
6. push 超时／返回不确定时先读取远端是否已包含目标 SHA，再决定重试。不重复创建相同提交。
7. 核对远端 main 包含候选 SHA，给出提交链接。只有项目已配置自动部署才继续监测；不承诺所有 main 推送都会上线。

## zhyq：推 test 后由 Agent 自查合 main

1. 从最新 `origin/test` 整合本次工作，完成相关检查及数据库检查，正常推 test，记录并核对本次 test SHA。
2. fetch main/test，读取两者间全部待上线提交。共享 test 可能有他人未发布改动；确保整批可发布。范围不明或有失败项，不把整条 test 送上生产。
3. 创建临时本地集成分支／worktree，基于最新 main 合入**已审查的固定 test SHA**。不审查一个 SHA 后又默默改为合入不断前进的 `origin/test`。
4. 在合并结果上完成项目要求的检查，详见 [zhyq.md](zhyq.md)。解决冲突后复验，不能只测试合并前的 test。
5. 推 main 前再 fetch；main 前进就重新整合验证。test 前进时明确新增内容是否属于本次，未审查的新提交留待后续。只推验证过的候选，遵守实际分支规则。
6. 正常推 main，核对远端包含候选 SHA。保留 test；需要时把已发布 main 合回最新 test 并正常推送，保留同事新提交，不能 reset test 到 main。
7. 若后来增加真正的自动提升流水线，先读触发条件并跟踪本次 SHA，避免 Agent 与流水线同时合并；旧快照不是永久规则。

## 部署与结束报告

GitHub Actions／外部流水线：按仓库、分支、工作流、head SHA 匹配运行；“最新一条成功”可能属于别人。没有匹配运行时报告未触发／待确认，不虚构检查结果。

服务器轮询：查看已获授权的部署日志、容器／运行版本和健康检查。checkout SHA 不能单独证明镜像已更新；失败或回滚如实报告。无版本标记时结合对应部署日志与本次功能验收，说明证据边界。

任务仍运行时进行有上限检查（例如 15 分钟），每次短间隔等待并提供有意义进展；超时说明最后状态及下一步，不无限等待。用户要求“稍后持续盯着”且宿主有调度工具时建立受支持监测；否则不承诺结束后后台轮询。

| 状态 | 所需证据 |
|---|---|
| 本地已启动 | 服务与关键访问实测通过 |
| 已推 test / main | 远端对应分支包含目标提交 |
| 检查通过 | 最终候选的要求项执行成功；未跑的另列 |
| 部署中 | 与目标版本相关的实际部署记录 |
| 已上线并验证 | 运行版本／对应部署记录 + 健康与本次功能验证 |
| 代码已推，线上待验证 | 只有 Git 证据，缺生产验收权限或观测入口 |

参考：[Git push 与 fast-forward](https://git-scm.com/docs/git-push)、[Git merge](https://git-scm.com/docs/git-merge)。
